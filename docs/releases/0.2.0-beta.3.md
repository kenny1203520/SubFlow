# SubFlow 0.2.0-beta.3 release qualification

Candidate branch: **chore/release-0.2.0-beta.3**, prepared from **origin/release/0.2.0-beta** at **a9ac0b9**, the merge of PR #81 together with PRs #82 to #85.

This document describes a candidate. It does not assert that the version tag, container image or GitHub release has been published.

## Why this release exists

An installation on 0.2.0-beta.1 ran normally for a day, restarted, and then refused every start with `previous upgrade failed (backup_failed)` after a nil-pointer panic. 0.2.0-beta.2 has the same defect. On both versions `subflow upgrade retry` cannot clear the state.

Cause, confirmed in the beta.1 source:

- `Complete` re-verified the recovery snapshot of an already finished upgrade on every start, and the reference to it was never cleared. Once the snapshot was no longer on disk the start failed.
- Any serve error was recorded as a failed upgrade, and the problem code was derived from words in the message, so a path under `.subflow/backups` was reported as `backup_failed`.
- The initial exchange-rate refresh started before completion and queried a database that the failed startup had already released.

## Included changes

- Stop recording serve errors after a completed upgrade as a failed upgrade. The process exits nonzero for its supervisor to restart and the upgrade state stays ready.
- Clear, at the next start, a failure that an earlier build recorded after completion, and write an `upgrade.recovered` audit event. Only codes a serve or finalize error produces qualify; without the audit record the failure stays. Operator blocks such as `unsupported_downgrade` and failures during backup, migration or verification still need `subflow upgrade retry`.
- Do not treat an ordinary restart interrupted during startup as an interrupted upgrade.
- Start the initial exchange-rate refresh after completion and contain panics in background jobs.
- Classify upgrade problem codes with typed errors at the source.
- Keep upgrade recovery snapshots out of PocketBase backup archives, check free space before copying, and remove the snapshot after a successful upgrade.
- Refresh reference exchange rates for every supported currency and base instead of aborting at the first unsupported code.
- Label every OAuth sign-in option with its provider name and one button style.
- Set explicit button types and statically analysable autocomplete values on several forms.

## Upgrading a locked beta.1 or beta.2 installation

Replace the image with 0.2.0-beta.3 and start normally, with the same data volume and encryption key. When `subflow upgrade status --state-only` showed `failurePhase` `ready` with `backup_failed`, the start clears it and continues. Take an offline copy of the whole data directory first.

The upgrade snapshot only protects the migration and is removed after success. PocketBase scheduled backups are off until a cron expression is set under Settings > Backups.

## Verification before this candidate (2026-11-15)

- PR #81 passed all 17 GitHub checks on the merged content: Verify, CodeQL (Go and JavaScript/TypeScript), the local SARIF gate, five browser projects, the migration core on three operating systems, the container build with the upgrade and backup-restore rehearsal from alpha.1 through beta.1, lint, and the SonarCloud quality gate.
- A locally built binary was started against a volume put into the beta.1 locked state by hand. It reached ready, wrote one `upgrade.recovered` event and the matching `audit_logs` row.
- Local results for this branch are recorded in the pull request.

## Not verified

- The rehearsal matrix does not include the published beta.2 image, and it has no scenario that reproduces the locked state inside a container. The lockout recovery is covered by unit tests and the manual run above only.
- A real bind failure after readiness was not reproduced; that path is covered by a unit test.
- 0.2.0-beta.1 and beta.2 images were not re-run against the fixed data path locally (no Docker daemon was available).
