# SubFlow 0.2.0-beta release qualification

The beta candidate is cut from `develop` at `bdd1f64` and keeps `master` on the stable line. It includes the changes integrated after Alpha 6, with PR #73's CAPTCHA settings retention and personal-ledger spacing fixes.

## Included changes

- Added an actionable home view and group settlement proposal and approval workflows.
- Added administrator-managed HTTPS certificate upload and reset controls, with backend audit events.
- Preserved CAPTCHA settings separately for each provider when verification is switched off or another provider is selected. Added explicit provider-data clearing and an append-only PocketBase migration for Alpha settings.
- Hardened application URL validation, share-cookie signing, migration recovery, and the production container runtime.

## Verification before tagging

- PR #73's required checks passed, including backend vet/tests, frontend tests/build, all five browser projects, migration core on Windows/macOS/Linux, container smoke, CodeQL and SonarCloud.
- Local `go test ./...` passed 529 tests across 16 packages; `go vet ./...` passed.
- Local frontend Vitest passed 167 tests and the production build passed.
- No open GitHub issues or pull requests were found while preparing this candidate.

## Beta testing focus

1. Upgrade a disposable copy of an Alpha installation. Verify login, ledger data, restart behavior, and the backup/restore path before using the beta with important data.
2. Exercise personal and group ledgers, settlement proposals/approvals, and role-based access.
3. Configure at least two CAPTCHA providers, switch between them, disable and re-enable verification, and confirm that clearing one provider leaves the other provider's settings intact.
4. Upload and reset a test HTTPS certificate, then check the admin and sign-in flows in your deployment environment.
5. Report the beta version, browser/OS, steps, expected result, actual result, and sanitized logs. Do not include credentials, tokens, or full private service URLs.

## Limits and publishing gates

Browser checks use desktop engines and touch emulation, not physical devices. External SMTP delivery and real CAPTCHA provider accounts are not exercised by CI. The tag workflow remains the final publishing gate: it validates release metadata, runs Verify and CodeQL, builds and smoke-tests the production container, rehearses the Alpha 1–5 upgrade/restore matrix, and only then publishes the GitHub pre-release and GHCR image.

This document describes candidate preparation and testing guidance; it does not claim publication succeeded. After the tag workflow completes, merge the release branch back into `develop` and leave `master` on stable.
